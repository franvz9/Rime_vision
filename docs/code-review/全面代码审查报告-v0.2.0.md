## 二、✅ 值得表扬的优秀实践

在讨论问题之前,先明确这个项目做对的地方——这些模式应当被保持和推广。

### ✅ P1: 原子写 + 全局锁(`rime/backup.rs`)

```rust
static WRITE_LOCK: Mutex<()> = Mutex::new(());

pub fn write_atomic(path: &Path, content: &str) -> Result<()> {
    let _guard = WRITE_LOCK.lock();
    // temp + rename 模式
}
```

**为什么好**: 文件写入用 temp+rename 保证原子性,全局 `parking_lot::Mutex` 防止并发写冲突。这是处理配置文件写入的正确方式,避免了"写到一半崩溃导致配置损坏"的常见陷阱。注释还解释了为何用同步锁而非异步锁——因为保护的 I/O 本身就是阻塞的。

### ✅ P2: 防竞态的 requestId 机制(`DictManager.vue`)

```typescript
let loadEntriesRequestId = 0

async function loadEntries() {
  const requestId = ++loadEntriesRequestId
  const result = await invoke<DictEntriesResult>(...)
  if (requestId === loadEntriesRequestId) {
    entries.value = result  // 只在仍是最新请求时更新
  }
}
```

**为什么好**: 快速切换词典或翻页时,异步请求可能乱序返回。这个递增 requestId 机制确保只有最新请求的结果会更新 UI,避免了"旧数据覆盖新数据"的闪烁 bug。比简单的 loading flag 更可靠。

### ✅ P3: RimeConfig 的 OnceLock 缓存(`rime/config.rs`)

```rust
fn cached_config() -> &'static RimeConfig {
    static CONFIG: OnceLock<RimeConfig> = OnceLock::new();
    CONFIG.get_or_init(RimeConfig::detect_inner)
}
```

**为什么好**: 用户目录路径在会话期间不变,缓存避免了每次命令调用都重新检测(尤其 Windows 上要检查 build/ 目录是否存在)。`OnceLock` 是线程安全的,适合 Tauri 多线程环境。

### ✅ P4: 类型安全的事件总线(`utils.ts`)

```typescript
export function emitBusEvent<K extends keyof BusEventMap>(name: K, detail: BusEventMap[K]) {
  window.dispatchEvent(new CustomEvent(name, { detail }))
}
```

**为什么好**: 把原生 `window.dispatchEvent(new CustomEvent(...))` 封装成泛型函数,事件名和 payload 类型绑定。编译期就能发现"派发了 A 事件但 payload 类型不对"的错误。比裸用 CustomEvent 安全得多。

### ✅ P5: 路径遍历防护体系

项目有完整的路径校验函数族:
- `validate_file_name()` — 阻止 `..`、绝对路径、null 字节
- `validate_dict_id()` — 只允许字母数字和 `_-`
- `validate_backup_id()` — 同上,长度限制 64
- `validate_import_path()` — 阻止路径遍历和控制字符

**为什么好**: 每个接受外部输入作为路径的入口都有校验,这是防御性编程的好实践。特别是 `copy_dir_filtered` 中遍历时也校验每个 entry 的文件名,防止恶意构造的备份目录。

### ✅ P6: cleanup_old_deploy_backups 的双重路径校验(`commands/backup.rs`)

```rust
fn cleanup_old_deploy_backups(max_count: usize) {
    // ...
    for (name, path) in backups.iter().skip(max_count) {
        if path.parent() != Some(&dir) {  // 二次校验
            eprintln!("Warning: refusing to remove backup outside deploy dir");
            continue;
        }
        // ...
    }
}
```

**为什么好**: `remove_dir_all` 是危险操作。这里在收集列表后、实际删除前,再次验证路径的父目录确实是 deploy 目录。即使第一次收集逻辑有 bug,这层校验也能兜底。这是"纵深防御"的正确体现。

## 三、🔴 Blocker 问题(必须修复)

### 🔴 B1: RimeError 定义但完全未使用,错误处理体系形同虚设

**文件**: `src-tauri/src/rime/error.rs` + 全部 49 个 Tauri command

**问题**:

`RimeError` 枚举定义完善(Io/Parse/Config/Permission/InvalidPath/NotFound/RateLimited/Unknown),带有 `thiserror` 和 `serde` 派生,甚至有 `From` 转换实现。但代码里标注了:

```rust
#[allow(dead_code)] // Reserved for v0.3.0 structured error migration
pub enum RimeError { ... }
```

而所有 49 个 Tauri command 仍然返回 `Result<T, String>`:

```rust
pub fn list_backups() -> Result<Vec<BackupInfo>, String>  // 应为 Result<_, RimeError>
pub fn restore_backup(...) -> Result<(), String>
pub fn delete_entries(...) -> Result<usize, String>
// ... 全部 49 个都是 String
```

**原因**: 这是系统性的架构缺陷,影响深远:

1. **前端无法区分错误类型**:所有错误都是字符串,前端只能靠 `String(e).includes('SYNC_NOT_CONFIGURED')` 这种脆弱的字符串匹配来判断错误类型(见 `DictManager.vue:153`)。一旦后端修改错误文案,前端就失效。
2. **错误信息不可靠**:大量 `map_err(|e| e.to_string())` 把结构化的 `io::Error` 压扁成字符串,丢失了错误种类(是 NotFound 还是 PermissionDenied?)。
3. **国际化困难**:错误文案硬编码在 Rust 里("文件操作失败"),前端无法按语言环境翻译。
4. **RimeError 的 From 实现成了死代码**:精心写的 `From<io::Error>` 映射(NotFound→NotFound, PermissionDenied→Permission)完全没被调用。

**建议**: 这是 v0.3.0 的首要任务。迁移步骤:

```rust
// 1. command 改用 RimeError
#[tauri::command]
pub fn list_backups() -> Result<Vec<BackupInfo>, RimeError> {
    // ...
    std::fs::read_dir(&dir).map_err(RimeError::from)?  // 现在会走 From<io::Error>
}

// 2. 前端用错误码判断,而非字符串匹配
try {
    await invoke('create_snapshot', {...})
} catch (e: { code: string, detail: string }) {
    if (e.code === 'Config') { /* 同步未配置 */ }
}
```

### 🔴 B2: 递归目录遍历无深度限制,存在栈溢出风险

**文件**: `src-tauri/src/rime/utils.rs:10-23, 32-43` + `commands/backup.rs:177-189`

**问题**:

`dir_size_recursive`、`count_files_recursive`、`collect_all_files` 都是无限递归:

```rust
fn dir_size_recursive(dir: &Path, size: &mut i64) {
    if let Ok(entries) = std::fs::read_dir(dir) {
        for entry in entries.flatten() {
            let path = entry.path();
            if path.is_file() { /* ... */ }
            else if path.is_dir() {
                dir_size_recursive(&path, size);  // 无深度限制
            }
        }
    }
}
```

**原因**: 

1. **符号链接循环**:如果目录树中存在符号链接循环(如 `a/b -> a/`),递归不会终止,最终栈溢出 panic。Rime 用户目录中 `lua/` 或 `opencc/` 可能包含符号链接。
2. **恶意构造的深层目录**:备份恢复时如果备份目录被篡改,构造极深的目录树,同样导致栈溢出。
3. `collect_all_files` 在 `copy_dir_filtered`(被 `restore_backup` 调用)中使用,属于关键路径。

**建议**: 增加深度参数:

```rust
const MAX_DIR_DEPTH: usize = 32;

fn dir_size_recursive(dir: &Path, size: &mut i64, depth: usize) {
    if depth > MAX_DIR_DEPTH {
        eprintln!("Warning: max directory depth exceeded at {:?}", dir);
        return;
    }
    if let Ok(entries) = std::fs::read_dir(dir) {
        for entry in entries.flatten() {
            let path = entry.path();
            // 跳过符号链接以防循环
            if path.is_symlink() { continue; }
            if path.is_file() { /* ... */ }
            else if path.is_dir() {
                dir_size_recursive(&path, size, depth + 1);
            }
        }
    }
}
```

### 🔴 B3: 异步组件无 errorComponent,加载失败白屏

**文件**: `src/App.vue:9-18`

**问题**:

```typescript
const GeneralSettings = defineAsyncComponent(() => import('./components/GeneralSettings.vue'))
const ThemeEditor = defineAsyncComponent(() => import('./components/ThemeEditor.vue'))
// ... 10 个异步组件,全部无 fallback
```

**原因**: `defineAsyncComponent` 默认情况下,如果动态 import 失败(网络问题、构建产物损坏、HMR 异常),组件渲染为空,用户看到白屏且无任何错误提示。生产环境打包后虽然单文件,但开发环境或增量更新时仍有风险。

**建议**:

```typescript
import { defineAsyncComponent, h } from 'vue'

const AsyncComponentLoader = (loader: () => Promise<any>) =>
  defineAsyncComponent({
    loader,
    loadingComponent: () => h('div', '加载中...'),
    errorComponent: () => h('div', { style: 'color:red' }, '组件加载失败,请刷新'),
    delay: 200,
    timeout: 10000,
  })

const GeneralSettings = AsyncComponentLoader(() => import('./components/GeneralSettings.vue'))
```

```rust

pub struct BackupInfo {
```

```typescript
// src/types/api.ts — 与 Rust 结构体一一对应,改动时同步
export interface BackupInfo { ... }
export interface DictEntry { ... }
// ...
```

```rust
fn cleanup_timestamped_backups(path: &Path, keep: usize) {
```

### 🟡 S3: restore_backup 函数过大(~200行),职责混杂

**文件**: `src-tauri/src/commands/backup.rs:471-670`

**问题**: `restore_backup` 单函数约 200 行,包含两条完全不同的执行路径:
- Full restore(483-588):auto-backup → staging → 原子 swap
- Partial restore(592-669):validate → stage → auto-backup → 逐文件替换

**原因**: 违反单一职责。两条路径的逻辑、错误处理、回滚策略都不同,混在一个函数里阅读困难,修改一条路径容易影响另一条。这也是之前记忆中"待拆分"的大函数。

**建议**: 拆分为两个独立函数:

```rust
#[tauri::command]
pub fn restore_backup(backup_id: String, restore_files: Vec<String>) -> Result<(), RimeError> {
    let cfg = RimeConfig::detect();

    if restore_files.is_empty() {
        restore_full(&cfg, &dir)
    } else {
        restore_partial(&cfg, &dir, restore_files)
    }
}

fn restore_full(cfg: &RimeConfig, dir: &Path) -> Result<(), RimeError> { /* ... */ }
fn restore_partial(cfg: &RimeConfig, dir: &Path, files: Vec<String>) -> Result<(), RimeError> { /* ... */ }
```

### 🟡 S6: 主项目无 CI,GitHub Actions 仅在 weasel 子目录

- `cargo check` + `cargo clippy -D warnings` + `cargo test`
- `vue-tsc --noEmit` + `eslint` + `prettier --check`
- 三平台矩阵(macos, windows, ubuntu)

```rust
pub fn export_user_dict(dict_id: String, output_path: String) -> Result<usize, String> {
    // ...
    if let Some(home) = dirs::home_dir() {
```

## 五、💭 Nit 问题(建议改进)

### 💭 N1: validate_file_name 与 validate_import_path 逻辑相似,可统一

`backup.rs:727` 的 `validate_file_name` 和 `dict.rs:8` 的 `validate_import_path` 都做路径安全校验,规则略有差异(后者允许路径分隔符)。考虑提取到 `rime/utils.rs` 并用枚举区分严格度。

### 💭 N2: package.json 缺少 lint/format/test 脚本

当前只有 `dev`/`build`/`preview`/`tauri`。补充后能让新贡献者一键运行检查。

### 💭 N3: Cargo.toml 依赖 thiserror 版本偏旧

`thiserror = "1"` 而最新是 2.x。虽功能够用,但可考虑升级以获得更好的诊断信息。

### 💭 N4: dirs::home_dir unwrap_or 兜底路径不合理

`config.rs:42` `unwrap_or_else(|| PathBuf::from("/Users"))` — 如果连 home 都获取不到,回退到 `/Users` 没有实际意义(普通用户无权写)。应返回错误或用更安全的回退(如当前目录)。

### 💭 N5: 注释中遗留英文与中文混用

部分函数文档用英文(`/// Calculate total size...`),部分用中文。建议统一为中文(面向用户的项目),或英文(开源贡献者友好)。当前混用略显随意。

### 7.1 攻击面分析

### 7.2 残留风险

1. **find_snapshot 信任 sync_dir**: `dict.rs:348` 从 `installation.yaml` 读取 `sync_dir` 后直接用作路径遍历起点,未校验范围。但这是用户自己配置的同步目录,风险可接受。

## 十、结语

WeaselVision 的代码质量在个人项目中属于上乘——安全意识强(路径校验、原子写、并发锁),架构清晰(三层分离),跨平台处理规范。之前三轮审查已修复了大部分即时风险。

当前的主要短板是**工程化基建**:错误处理体系未落地、测试覆盖极低、无 CI 和 lint 工具链。这些不是"bug",而是"技术债",不会立即爆发,但会持续拖慢开发速度、增加回归风险。

配套的《代码审查标准与流程》文档正是为了系统化地偿还这些技术债,把"审查"从事件驱动变为制度驱动。建议从 P0/P1 项开始,逐步建立 CI 和测试基建,再推进 B1 的错误处理迁移。
