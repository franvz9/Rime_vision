# WeaselVision 代码审查标准与流程

> 版本: 1.0 | 适用项目: WeaselVision (Tauri 2.0 + Vue 3 + TypeScript + Rust)
> 制定日期: 2026-07-01 | 维护者: 代码审查专家

---

## 一、为什么需要这套标准

WeaselVision 已经历三轮代码审查,累计修复 32 个问题,但审查始终是"事件驱动"的——发现问题才审查。这种模式有两个根本缺陷:

1. **不可持续**:每次审查都在补窟窿,而非防止窟窿产生
2. **标准漂移**:不同轮次由不同视角审查,严重程度判定和验收标准不一致

本标准的目标是建立**可持续、可量化、无偏见**的审查机制,让代码质量从"事后修复"转向"事前预防"。

## 二、审查流程

### 2.1 三层审查模型

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: 自动化审查 (CI Gate)  — 每次提交自动执行    │
├─────────────────────────────────────────────────────┤
│  Layer 2: 同伴审查 (PR Review)  — 合并前人工审查     │
├─────────────────────────────────────────────────────┤
│  Layer 3: 深度审查 (Deep Audit) — 每个里程碑定期执行 │
└─────────────────────────────────────────────────────┘
```

### 2.2 Layer 1:自动化审查(CI Gate)

**触发**:每次 push / PR。**必须全部通过才能进入 Layer 2。**

| 检查项 | 工具 | 阻断条件 |
|--------|------|----------|
| Rust 编译 | `cargo check` | 任何 error |
| Rust 告警 | `cargo clippy -- -D warnings` | 任何 warning |
| Rust 格式 | `cargo fmt --check` | 格式不符 |
| Rust 测试 | `cargo test` | 测试失败 |
| TS 类型 | `vue-tsc --noEmit` | 任何 error |
| TS Lint | `eslint src/` | 任何 error |
| TS 格式 | `prettier --check src/` | 格式不符 |
| 安全审计 | `cargo audit` | 已知 CVE |
| 依赖检查 | `npm audit` | high/critical 漏洞 |

### 2.3 Layer 2:同伴审查(PR Review)

**触发**:PR 创建时。**至少 1 人 approve 才可合并。**

审查时效要求:
- 24 小时内首次响应
- 48 小时内完成审查
- 超时自动提醒,7 天未审查由维护者接管

### 2.4 Layer 3:深度审查(Deep Audit)

**触发**:每个版本发布前(v0.3.0, v0.4.0...)或重大架构变更。

由代码审查专家执行,覆盖:
- 全量代码扫描(非增量)
- 架构合理性评估
- 安全专项审计
- 跨平台兼容性验证
- 技术债盘点与优先级排序

输出标准化的《深度审查报告》,归档至 `docs/code-review/`。

## 三、审查标准(分语言)

### 3.1 通用规则(适用于所有语言)

#### 🔴 Blocker(必须修复,阻断合并)

| 编号 | 规则 | 说明 |
|------|------|------|
| G-B1 | 安全漏洞 | 注入(XSS/SQL/命令)、认证绕过、路径遍历、不安全反序列化 |
| G-B2 | 数据丢失风险 | 写操作无原子保护、并发写无锁、删除操作无校验 |
| G-B3 | 竞态条件 | 共享状态无同步、TOCTOU 漏洞、死锁 |
| G-B4 | API 契约破坏 | 函数签名变更未同步调用方、返回类型不一致 |
| G-B5 | 关键路径缺错误处理 | 文件 I/O、网络、外部进程调用无 error 分支 |
| G-B6 | 硬编码敏感信息 | 密钥、token、绝对路径写入源码 |

#### 🟡 Suggestion(应当修复,强烈建议)

| 编号 | 规则 | 说明 |
|------|------|------|
| G-S1 | 输入校验缺失 | 外部输入(用户、文件、IPC)未做边界检查 |
| G-S2 | 命名歧义 | 变量/函数名无法表达意图,需读实现才能理解 |
| G-S3 | 重要行为无测试 | 核心业务逻辑、边界条件、错误路径未覆盖 |
| G-S4 | 性能问题 | N+1 查询、不必要的全量加载、同步阻塞异步线程 |
| G-S5 | 代码重复 | 超过 10 行的逻辑在 2+ 处重复,应提取 |
| G-S6 | 错误处理不一致 | 同类操作有的用 `?` 有的用 `match`,前端错误展示方式不统一 |

#### 💭 Nit(建议改进,不阻断)

| 编号 | 规则 | 说明 |
|------|------|------|
| G-N1 | 风格不一致 | linter 未覆盖的细节,如注释格式 |
| G-N2 | 命名优化 | 缩写过多、可更表意 |
| G-N3 | 文档缺失 | 公开 API 无文档注释,复杂逻辑无说明 |
| G-N4 | 魔法数字 | 硬编码数字/字符串应提为常量 |

### 3.2 Rust 后端审查标准

#### 3.2.1 安全专项

| 编号 | 规则 | 级别 |
|------|------|------|
| R-SEC1 | 所有接受用户输入路径的函数必须调用路径校验(`validate_file_name` / `validate_dict_id` 等) | 🔴 |
| R-SEC2 | 路径校验必须阻止: `..`、绝对路径前缀(`/` `\\`)、null 字节、控制字符 | 🔴 |
| R-SEC3 | `std::fs::remove_dir_all` 调用前必须验证目标路径在预期目录内 | 🔴 |
| R-SEC4 | 外部命令执行禁止用 shell(`sh -c`),必须用 `Command::new` 直接调用或用安全 crate | 🔴 |
| R-SEC5 | YAML/JSON 解析必须限制文件大小(当前 `MAX_YAML_SIZE = 10MB`) | 🟡 |
| R-SEC6 | `unwrap()` / `expect()` 禁止出现在生产路径(仅允许测试和 `OnceLock::get_or_init`) | 🟡 |

#### 3.2.2 错误处理

| 编号 | 规则 | 级别 |
|------|------|------|
| R-ERR1 | Tauri command 的错误类型必须能向前端传递结构化信息(禁止裸 `Result<T, String>`) | 🔴 |
| R-ERR2 | `map_err(|e| e.to_string())` 丢失了错误上下文,应转为结构化错误 | 🟡 |
| R-ERR3 | 错误信息面向用户,用中文,说明"什么失败了"和"可能的原因" | 🟡 |
| R-ERR4 | `eprintln!` 仅用于调试;面向用户的错误必须通过 `Result` 返回 | 💭 |

> **当前状态**: `RimeError` 已定义但全部 command 仍返回 `Result<T, String>`,违反 R-ERR1。这是 v0.3.0 的首要迁移任务。

#### 3.2.3 并发与 I/O

| 编号 | 规则 | 级别 |
|------|------|------|
| R-CON1 | 所有文件写操作必须经过 `write_atomic`(temp + rename) | 🔴 |
| R-CON2 | 跨命令共享的可变状态必须用 `Mutex`/`RwLock` 保护 | 🔴 |
| R-CON3 | 同步 I/O(文件读写)在 async command 中必须用 `spawn_blocking`,禁止阻塞 Tokio 运行时 | 🟡 |
| R-CON4 | 锁的持有时间应最小化,禁止在持锁时执行 I/O 以外的耗时操作 | 🟡 |
| R-CON5 | 递归函数(如目录遍历)必须有深度限制,防止符号链接循环导致栈溢出 | 🟡 |

#### 3.2.4 跨平台

| 编号 | 规则 | 级别 |
|------|------|------|
| R-XPL1 | 平台差异必须用 `cfg!(target_os = ...)` 编译期分支,禁止运行时判断 OS | 🟡 |
| R-XPL2 | 路径拼接必须用 `Path::join`,禁止字符串拼接路径分隔符 | 🔴 |
| R-XPL3 | Windows 文件锁(`.log` `LOCK` `MANIFEST-`)需特殊处理,已有模式应复用 | 🟡 |
| R-XPL4 | 字体、编码等平台相关配置须提供回退链 | 💭 |

#### 3.2.5 代码组织

| 编号 | 规则 | 级别 |
|------|------|------|
| R-ORG1 | 单个函数不超过 80 行;超过则拆分 | 🟡 |
| R-ORG2 | `commands/` 层只做参数校验和调度,业务逻辑放 `rime/` 层 | 🟡 |
| R-ORG3 | 公共工具函数统一放 `rime/utils.rs`,禁止在 command 模块内重复定义 | 🟡 |
| R-ORG4 | `#[allow(dead_code)]` 必须附带 `TODO(version)` 注明启用计划 | 💭 |

### 3.3 前端 (Vue 3 + TypeScript) 审查标准

#### 3.3.1 类型安全

| 编号 | 规则 | 级别 |
|------|------|------|
| F-TS1 | 禁止 `any` 类型(必要时用 `unknown` + 类型守卫) | 🟡 |
| F-TS2 | 与后端交互的数据结构必须有 TypeScript interface 定义 | 🟡 |
| F-TS3 | `invoke()` 调用必须带泛型:`invoke<ReturnType>('cmd', params)` | 🟡 |
| F-TS4 | 后端返回的数据结构应有单一数据源(SSoT),禁止前后端各定义一份 | 🟡 |

> **当前状态**: `BackupInfo`、`DictEntry` 等在 Rust 和 Vue 中各定义一次,违反 F-TS4。建议用 `tsrs` 或手写 `types/api.ts` 集中管理。

#### 3.3.2 组件设计

| 编号 | 规则 | 级别 |
|------|------|------|
| F-VUE1 | 公共 UI(Modal/Button/Tabs/Toast)必须提取为独立组件,禁止在业务组件内重复定义 | 🟡 |
| F-VUE2 | 组件内 CSS 超过 200 行应评估提取 scoped 样式或公共类 | 💭 |
| F-VUE3 | `defineAsyncComponent` 必须提供 `errorComponent` 和 `loadingComponent` | 🟡 |
| F-VUE4 | 事件监听(`addEventListener`)必须在 `onUnmounted` 清理,或用 `onBusEvent` 的返回值取消 | 🔴 |

#### 3.3.3 状态与副作用

| 编号 | 规则 | 级别 |
|------|------|------|
| F-ST1 | 异步请求须防竞态(用 requestId 递增机制或 AbortController) | 🟡 |
| F-ST2 | `setTimeout`/`setInterval` 必须在 `onUnmounted` 清理 | 🔴 |
| F-ST3 | 全局状态优先用 composable(如 `useToast`),避免事件总线滥用 | 🟡 |
| F-ST4 | 错误必须经 `errorMessage()` 统一处理后展示,禁止直接 `String(e)` | 🟡 |

#### 3.3.4 用户体验

| 编号 | 规则 | 级别 |
|------|------|------|
| F-UX1 | 所有异步操作必须有 loading 状态和 disabled 按钮 | 🟡 |
| F-UX2 | 危险操作(删除、清空)必须有二次确认 | 🔴 |
| F-UX3 | 错误提示用 `toast.error`,成功用 `toast.success`,禁止 `alert`/`confirm` | 🟡 |

---

### 3.4 IPC 接口审查标准

| 编号 | 规则 | 级别 |
|------|------|------|
| I-1 | 每个 Tauri command 必须在 `lib.rs` 的 `invoke_handler` 注册 | 🔴 |
| I-2 | command 参数必须是可序列化类型,蛇形命名(snake_case) | 🟡 |
| I-3 | 前端调用参数名须与 Rust 函数参数名一致(含驼峰转蛇形) | 🟡 |
| I-4 | 新增 command 须更新 IPC 契约文档(命令名、参数、返回值、错误码) | 🟡 |
| I-5 | 错误返回须包含错误码,前端可据此决定恢复动作 | 🟡 |

## 四、审查评论规范

### 4.1 评论格式

每条评论必须包含三要素:**问题 + 原因 + 建议**。

```markdown
🔴 **[类别]: 简短标题**
文件:行号

**问题**: 具体描述哪里有问题。

**原因**: 为什么这是问题(影响是什么)。

**建议**: 
\`\`\`rust
// 建议的修改方式
\`\`\`
```

### 4.2 类别标签

- `🔴 Blocker` — 必须修复才能合并
- `🟡 Suggestion` — 强烈建议修复,可创建后续 issue
- `💭 Nit` — 可选改进,不强制
- `✅ Praise` — 值得学习的优秀实践,必须点名表扬

### 4.3 审查者行为准则

1. **对事不对人**:评论代码,不评论人。"这段逻辑有竞态风险"而非"你怎么没考虑并发"
2. **解释为什么**:不止说"改这个",要说清"为什么要改"
3. **提问优于断言**:意图不明时先问"这里是否考虑了 X 场景?",而非直接判定错误
4. **限定范围**:只审查代码质量,不审查个人偏好(缩进、命名风格交给 linter)
5. **表扬好代码**:发现优秀实践必须明确指出,这比批评更有激励作用
6. **不重复劳动**:linter/CI 能查的(格式、未用变量)不人工重复

## 五、技术债管理

### 5.1 技术债登记

所有审查中发现的 Suggestion/Nit 若不在本次 PR 修复,必须登记到技术债清单。

技术债记录格式:

```markdown
### TD-XXX: 简短标题
- **来源**: Round X 审查 / PR #XX
- **级别**: 🟡 Suggestion
- **位置**: 文件:行号
- **描述**: 问题描述
- **建议方案**: 修复思路
- **计划版本**: v0.3.0
- **状态**: 待办 / 进行中 / 已修复
```

技术债清单维护在 `docs/code-review/技术债清单.md`。

### 5.2 技术债优先级矩阵

```
        高影响
          │
   先修复  │  规划修复
  ────────┼────────
   容忍    │  低优先
          │
        低影响
   低成本 ←──────→ 高成本
```

- **先修复**:高影响 + 低成本 → 立即修复
- **规划修复**:高影响 + 高成本 → 纳入版本规划
- **容忍**:低影响 + 低成本 → 顺带修复
- **低优先**:低影响 + 高成本 → 记录但不主动处理

## 六、度量指标

### 6.1 代码质量指标

| 指标 | 目标 | 当前 | 采集方式 |
|------|------|------|----------|
| Rust 测试覆盖率 | ≥60% | ~5% | `cargo tarpaulin` |
| 前端测试覆盖率 | ≥40% | 0% | `vitest --coverage` |
| Clippy 告警数 | 0 | 待测 | CI |
| ESLint error 数 | 0 | 待测(未配置) | CI |
| `any` 类型使用数 | ≤5 | 待测 | grep 统计 |
| 函数平均行数 | ≤40 | 待测 | 脚本统计 |
| Blocker 缺陷密度 | <1/kLOC | 待测 | 审查报告 |

### 6.2 审查过程指标

| 指标 | 目标 | 采集方式 |
|------|------|----------|
| PR 审查响应时间 | <24h | GitHub 统计 |
| PR 审查完成时间 | <48h | GitHub 统计 |
| CI 通过率 | ≥95% | GitHub Actions |
| 审查评论中 Praise 占比 | ≥20% | 人工统计 |

> PR 提交前自检 / 审查者审查时逐项确认
